# operating/linear.md — the tracker, and the safety line

**Purpose.** The tracker (Linear by default) is the single place you follow the whole project: the
backlog, what is in flight, what has landed dark on dev, what is **awaiting your call**, and the PRs
(with deploy previews inline). It is the live tracker + review/decision queue. The `operating/` docs
stay the orchestrator's operating memory; the tracker is the tracker, not the archive.

For setup from zero (workspace, states, labels, API key, GitHub sync), see `integrations/linear.md`.
This file is the conventions and the non-negotiable safety line.

---

## The safety line (non-negotiable)

The tracker is **third-party SaaS**. Treat everything in it as potentially exportable, outside your
infra. If a fact would be unsafe in a public git commit, it is unsafe in the tracker.

**NEVER put in the tracker:**
- Private user data of any kind — real names, emails, domains, phone numbers, PII; message / email /
  document content; CRM records.
- Secrets, credentials, API keys, tokens, connection strings, or private URLs carrying a token.
- Anything sourced from a customer's connector or from a private archive.

**What DOES go in the tracker:** your own work — features, bugs, specs at the metadata level,
decisions, PR links, deploy-preview URLs, your own code (kept clean by rule), infra/ops tasks, and
counts/booleans. When a detail is sensitive, **link to a private doc instead of pasting it**.

**Structural safety:** keep the workspace private/invite-only; do **not** connect user-data
integrations (a support inbox, email) that would sync PII in; GitHub sync is fine (your code is clean
by rule); prefer links over pasted content, always.

## Structure (the shape to build)

- **States (mirror the pipeline):** `Backlog` → `Todo` (specced/ready) → `In Progress` →
  `In Review` → **`On DEV — QA owed`** → **`On DEV — QA done`** (your inbox) → `Done`; plus `Blocked`,
  `Canceled`, `Duplicate`.
- **Labels:** `area/backend` · `area/frontend` · `area/infra` · `type/feature` · `type/bug` ·
  `type/chore` · `type/decision` · `triage/needs-triage` · `triage/ready-for-agent` ·
  `triage/ready-for-human` · `triage/wontfix` · `needs-you` · `risk:prod`.
- **`On DEV — QA done` + `needs-you` = your single inbox** — everything gated on your call, each
  carrying the diff, the QA evidence, and a preview URL you can click.

## The filing flow

At each pipeline gate the orchestrator files/updates an issue with the evidence template from
`operating/workflow.md` §6. The issue body is the brief (Agent Brief shape). Every AI-written comment
starts `> *Generated by the orchestrator.*` Decision and Blocked issues start with the ask:
- A `Decision needed` issue opens with **Question** (one sentence), **Options** (2–3, one line each),
  **Recommendation** (one, with the reason), **Since / Unblocks**.
- A `Blocked` issue opens with **By** (who/what, named), **Since**, **What unblocks it** (the concrete
  event), **Next check**.

So you read the top four lines and decide; you never have to dig.

## Headless access

Interactive connectors use OAuth and do not work in an unattended session. An unattended agent talks
to the tracker's API with an API key in its environment (you create it once; it is a secret, so it
never enters a chat). An interactive session keeps using the connector. Same pattern for Sentry and
PostHog.
